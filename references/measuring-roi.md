# 怎么自己衡量 AI 投入的回报

> 本 skill 打的是**协作方式的成熟度分**，不是 ROI。这两件事经常被混为一谈：
> 成熟度高说明「你把事情做对的概率高」，不等于「这季度确实赚回来了」。
> 本文讲的是后者——你自己怎么量。

## 一、先破三个常见误区

**误区 1：ROI = 省下的人力 ÷ token 花的钱。**
token 成本通常是这笔账里最小、也最不重要的一项。真正的成本在**验证**——
DORA 把它叫「验证税」：AI 产出越多，人核对的负担越重。一个团队完全可能 token 花得很少，
却因为返工把收益吃光。**先量验证税，再量 token。**

**误区 2：提交量 / 代码行数 / PR 数涨了 = 有回报。**
这是最容易骗自己的一组数。AI 会**机械地**抬高这些数字：更细的提交、更多的重构、
更啰嗦的实现。它们是**活动量**，不是**产出**。活动量只有一个正当用途——
当分母，用来算「每单位活动带来多少返工」。单独看它涨了 20 倍，什么都证明不了。

**误区 3：「只要方法做对了，回报一定好。」**
方向上没错，但它把「做对了」当成已知条件，而这恰恰是要测的东西。
AI 是**放大器**：放大好流程，也放大坏流程。真实的例子就在本 skill 的第一份报告里——
团队的约束层（hooks、门禁、worktree、规格层）做得比业界多数团队都好，
自我感觉也是「做对了」；但把窗口从 90 天拉到 14 个月看，**两个有 AI 之前历史的老仓，
返工率在同一个月里从 10–20% 跳到 60% 以上**。没有这条曲线，谁都不会发现。

所以顺序是：**先量，再判断做没做对**，不是反过来。

## 二、分三层量，从不花钱的开始

### 第 0 层 · git 里已经有了（`scan.py --trend 12` 直接产出）

不需要任何新工具、新流程，只要仓库有历史。

| 指标 | 算法 | 怎么读 |
|---|---|---|
| **返工率** | `fix / (fix + feat)` 按月 | **最有价值的单个数**，是「验证税」的直接代理。但它是**构成比不是质量分**，没有及格线——见下方「怎么读返工率」 |
| **回滚 / 紧急修复数** | subject 含 revert/hotfix/回滚 | 变更失败率的粗代理。低频事件，看季度不看月 |
| **吞吐** | 合并 PR / 月 | 只当分母用 |
| **AI 归属率** | trailer + 分支名两条路 | 用来确认「变化是不是真跟 AI 有关」，不是成绩 |
| **PR 体量** | 每 PR 平均改动行数 | 变大 = 评审者审不动 = 返工的前兆 |
| **测试耦合度** | AI 署名 commit 中同时改了测试的比例 | 认知债代理。低于 50% 要警惕 |

**怎么读返工率（最容易被误用的一个数）：**

| 团队所处阶段 | 返工率天然的样子 | 说明 |
|---|---|---|
| 新项目开荒 | 低 | 大部分提交是新功能，正常 |
| 成熟产品维护期 | **高** | 本来就该以修为主，**高是健康的** |
| 发版前稳定 / UAT | **冲高** | 缺陷被拦在交付前，**是系统在正常工作** |
| 交付后线上频繁救火 | 高 | 这才是不健康的那种高 |

所以绝对值没有意义，**任何「低于 X% 才合格」的说法都是编的**。它只在两个前提下可读：
① 跟自己的历史比；② 生命周期阶段大致可比。

还有一个前提容易漏：**先看「可分类提交比例」**（subject 带 `fix` / `feat` 前缀的占比）。
如果这个比例本身在变（团队换了提交规范、新人不写前缀），返工率的趋势就是假的。
本 skill 第一次用时专门验过这一条，确认可分类率全程 81–100% 才敢下结论。

**组合起来读，单看一个都会误判：**

| 吞吐 | 返工 | 结论 |
|---|---|---|
| ↑ | 持平 | **真实收益**。这是你要的形状 |
| ↑ | ↑ | 在**用返工换吞吐**。收益被验证税吃掉多少，取决于两者涨幅差 |
| ↑↑ | ↑↑ | 危险。产得比理解得快，典型的认知债积累 |
| 持平 | ↓ | 也是收益——同样的产出，质量成本更低 |

### 第 1 层 · 十几分钟能接上（要一点点流程配合）

| 指标 | 怎么拿 | 为什么值得 |
|---|---|---|
| **前置时间**（首次提交 → 合并） | git 里就有：PR 合并时间 − 该分支首个 commit 时间 | DORA 四指标里唯一能纯靠 git 算的，直接反映流动效率 |
| **评审等待时间** | 平台 API（PR 创建 → 首个 review） | AI 提效后最常见的新瓶颈就是评审排队 |
| **验收打回次数** | 任务系统里加一个「打回」状态即可 | 比任何代码指标都接近「客户是否满意」 |
| **CI 一次通过率** | CI 平台自带 | 掉下去说明本地门禁形同虚设 |

### 第 2 层 · 需要真的投入（想清楚再做）

- **部署频率 / 恢复时间**：补齐 DORA 四指标，要发布流水线配合。
- **缺陷逃逸率**：线上缺陷数 ÷ 交付需求数。**这才是你说的「fix bug 变少了」的正确形式**——
  注意不是「代码里 fix 提交变少」（那是返工率，是内部指标），而是**用户遇到的问题变少**。
  两者可能反向：内部 fix 多恰恰可能意味着逃逸少。
- **token / 订阅成本**：放最后。有了上面的数，这个数才有分母可比。

## 三、关于「fix bug 变少了」

这是个好直觉，但要分清两种 bug，否则会得出相反结论：

| | 含义 | 变少是好是坏 |
|---|---|---|
| **内部 fix 提交**（返工率） | 交付前自己发现并修 | 变少通常是好事，但**如果是因为没测出来**，就是坏事 |
| **线上缺陷**（逃逸率） | 用户遇到了 | 变少一定是好事 |

**只看内部 fix 会骗人**：一个团队可能因为测试变弱，内部 fix 变少、线上缺陷变多。
所以这两个数要**一起看**：内部 fix 高 + 线上缺陷低 = 健康（拦在了交付前）；
内部 fix 低 + 线上缺陷高 = 危险。

## 四、建议的最小起步

1. 跑 `scan.py --trend 12`，把返工率曲线贴进周报。**只要这一条**，坚持 8 周。
2. 同时记一个手工数字：本季度验收打回次数。
3. 8 周后跑 `scan.py --compare`，看返工率有没有跟着治理动作往下走。
4. 前三步稳定了，再考虑加前置时间和缺陷逃逸率。

不要一次上十个指标。**没人看的指标等于没有指标**——本 skill 评估过的项目里，
就有一个自动巡检例程连续 61 次输出「无新增」后静默停摆 23 天，没人发现。
