# 分析报告模板（markdown 事实源）

报告分两层：**markdown 是事实源**（可进项目文档、可 diff），**HTML / PDF 是展示层**（由 `report.json` 驱动脚本生成）。
先写 markdown，再把数字和段落填进 `report.json`。两处数字必须一致——写完用 grep 抽查三个关键数。

front-matter（按项目文档规范调整；没有规范就至少写这四项）：

```yaml
---
title: <项目名> AI 协作开发成熟度评估与优化方案
owner: <评估人>
updated: <YYYY-MM-DD>
baseline: <各仓 origin/<branch> @ 日期；规格台账规模>
---
```

## 六节固定结构

### 一、一句话结论

三句话，顺序不能换：**位置**（L 几、几分）→ **瓶颈**（短板在哪三处）→ **下一阶段主题**（一句话）。
后面加一段「与上次相比」：哪些维度升了、哪些降了、总分变化。第一次体检没有上次，写「基线」。

### 二、外部范式

一张表：来源 / 时间 / 对本项目最相关的结论。只放**本次打分实际用到的**范式，不堆砌。
表后一段说明 9 个维度从哪来。范式超过 6 个月要先刷新（见 paradigms-2026.md 末尾）。

### 三、现状证据

先放 4 个 KPI（吞吐、合并 PR、最刺眼的风险数、集中度），再放图表，再放「治理层盘点」表（层 / 已有 / 缺口，9 行对应 9 维度）。
最后一段「已有的自我认知」：项目里以前的体检、ADR、复盘已经指出过什么、有没有收敛——**发现问题的机制有没有，收敛问题的机制有没有**，这是最值钱的判断。

数字写法：每个数字要能回溯到 scan.json 的字段或人工核对项；用「近 90 天，origin/main」这类口径前缀。

### 四、成熟度打分

打分表（维度 / 分 / 依据 / 参照）+ 一段「与业界对照的位置」：哪些维度领先、哪些持平、哪些落后一代。
依据一栏必须指到数据或文件，不写「感觉还行」。

### 五、优化方案

分三波：**两周止血**（低成本高杠杆）/ **一到两月建闭环**（反馈控制）/ **一个季度度量与规模化**。
每条四件套：做什么 / 为什么（指向范式或数据）/ 落点（文件、配置、人）/ 验收指标。
后面必有两块：**明确不做的事**（减法）和**下次重打分目标**（哪几个维度要升到几分）。

优化项写法示例：

| # | 做什么 | 为什么 | 落点 | 验收指标 |
|---|---|---|---|---|
| 1 | 各子仓加 ≤100 行 CLAUDE.md，只写地图、命令、红线、指向文档 | 子仓主线上 0 行上下文；OpenAI 实证地图式短文件最有效 | 各仓 CLAUDE.md 走 PR | 各仓主线存在且 ≤100 行 |

### 附录 · 资料来源

来源列表 + 一行统计口径说明（窗口、分支、AI 署名判定规则）。

## 常见写作错误

- 把「某人 commit 占比高」写成「没用 AI」。拆成写 / 合 / 验三件事，旁边放各人 AI 署名率。
- 把同步合并当评审合并。只用脚本的 `merge_authors`（PR 合并），别用 `git log --merges` 裸数。
- 把厂商数字（PR +67%）当目标。目标只对自己的基线。
- 方案只有加法。每次都要有「不做什么」。
- 建议没落点。「加强评审」不算建议，「评审策略文件加 reviewer 字段，门禁 hook 校验」才算。
- 忘了说口径。「AI 署名率」不说明是 trailer 下限，读者会当成真实使用率。
- 手数代替脚本。手工 ls 出来的台账数和脚本差过 9 个；以脚本为准，脚本错了改脚本。
- 在图表 caption / KPI label 里写 HTML 标签。这些字段会被转义，`<b>` 会原样印进 PDF；只有表格行和 `*_html` 字段吃 HTML（清单见 `assets/report.template.json` 的 `_doc_html_fields`）。
